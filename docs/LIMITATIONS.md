# ArtifactX — Forensic Limitations & Scope Boundaries

> **Document Version:** 1.0.0 (Phase A Baseline)  
> **Audience:** Forensic Examiners, Analysts, and Reviewers  
> **Rule Reference:** Enforces Master Rules R1, R7, R8, R9, R20

---

## 1. Overview

This document specifies the forensic boundaries, technical limitations, and scope constraints of ArtifactX. Forensic integrity requires transparent declaration of what the tool cannot do, what assumptions it relies upon, and where automated findings require independent human verification.

---

## 2. Cryptographic & Decryption Boundaries

### 2.1 No Key-Less Decryption
ArtifactX does not, and cannot, decrypt encrypted artifacts without valid, matching cryptographic key material:
- Neither WhatsApp `.crypt12`, `.crypt14`, `.crypt15` databases nor SQLCipher containers can be decrypted without the corresponding encryption keys.
- When an encrypted file is presented without key material, ArtifactX calculates its cryptographic hashes, measures entropy, and flags the artifact honestly as `ENCRYPTED_KEY_REQUIRED` or `UNKNOWN_ENCRYPTED_KEY_REQUIRED`. It does not attempt dictionary attacks, brute-force recovery, or undocumented bypasses.

### 2.2 WhatsApp Crypt15 Offline Key Requirements
Offline decryption of WhatsApp `.crypt15` backup databases requires:
- The raw **64-character hexadecimal root encryption key**, or
- The raw binary key file (`encrypted_backup.key`).
- **Passphrase Limitation:** User-facing backup passphrases cannot be decrypted purely offline. WhatsApp passphrases rely on remote server-side Key Vault interaction. ArtifactX operates strictly offline and network-isolated (R13); therefore, passphrases are not supported for offline `.crypt15` derivation (DEC-002).

### 2.3 Telegram Secret Chats & MTProto
- **Secret Chats:** Telegram End-to-End Encrypted (E2EE) "Secret Chats" are ephemeral, stored separately with ephemeral keys, and are not parsed from the standard Android `cache4.db` database.
- **MTProto Protocol:** MTProto network packet decryption requires the ephemeral session `auth_key` held in transient memory or captured network traffic. ArtifactX parses at-rest database extractions and does not perform network packet MTProto decryption.

## 3. Data Recovery & Deletion Indicators

### 3.1 ID Sequence Gaps as Weak Heuristic Indicators
- **Limitation:** Missing row IDs or sequence gaps in message tables are classified strictly as **weak indicators** (`strength="weak_hint"`, with `confidence_score ≤ 0.30` per DEC-014).
- **Caveat:** Gaps in auto-incrementing integer sequences do not prove intentional deletion. Gaps frequently arise from network dropouts during sync, server-side message assignment anomalies, failed transactions, or normal database vacuuming. ID gaps are never summed into verified deletion totals and are not placed on the primary timeline.

### 3.2 Recovery from SQLite Freelist and Unallocated Space
- Recovery of deleted messages from SQLite freelists, WAL (Write-Ahead Log) frame histories, and page unallocated space depends entirely on whether deleted records have been overwritten by subsequent transactions or purged by `VACUUM` operations.
- Overwritten or vacuumed records cannot be recovered.

## 4. Platform, Format & Architecture Scope

### 4.1 Unsupported Platforms and Artifact Types
- **Telegram Desktop (`tdata`):** The proprietary binary `tdata` directory format used by Telegram Desktop is out of scope and unsupported.
- **Apple iOS Extractions:** iOS-specific database layouts (such as iOS WhatsApp `ChatStorage.sqlite`) are out of scope. ArtifactX is targeted specifically to Android mobile extractions (`msgstore.db` and Android `cache4.db`).

### 4.2 Synthetic-Fixture Validation Baseline (Deferred V1)
- **Validation Scope:** Forensic parsers, carving routines, and decryptors in ArtifactX are implemented against documented format standards and validated against reproducible synthetic ground-truth fixtures.
- **Physical Device Extractions:** Validation against physical mobile acquisitions from various Android OEM flavors is deferred to examiner verification (Deferred V1).

---

## 5. Temporal & Environmental Limitations

### 5.1 Device Clock Skew and Timezone Anomalies
- Timestamps extracted from SQLite records and EXIF metadata originate from the subject device's local system clock or the remote messaging server clock.
- If the device clock was misconfigured, drifted, or intentionally altered, extracted timestamps will reflect that anomaly. ArtifactX preserves original raw timestamps alongside normalized UTC timestamps and flags temporal anomalies, but cannot independently verify physical ground-truth time without external reference logs.

## 6. Legal & Reporting Scope

### 6.1 Section 63 BSA 2023 Draft Nature
- All certificates, hash declarations, and Section 63 BSA (Bharatiya Sakshya Adhiniyam) documentation generated by ArtifactX are **drafts for expert review**.
- ArtifactX provides data summaries, cryptographic hashes, and provenance trails, but cannot substitute for the testimony, qualifications, or independent verification of a qualified digital forensic examiner.

### 6.2 Corroboration Requirement
- Automated correlations (phone numbers, cryptocurrency addresses, near-duplicate images) represent investigative hypotheses and indicators. Every finding must be corroborated by independent sources before being relied upon in legal or administrative proceedings.

## 7. Ingestion, Memory Ceilings & Streaming Boundaries (B5.1, B5.7, DEC-012, DEC-026)

### 7.1 Exhibit Size Ceiling (MAX_UPLOAD_SIZE)
- The global maximum upload size ceiling is configured via `MAX_UPLOAD_SIZE` (default: **256 MiB** / `268,435,456` bytes).
- Streams or uploads exceeding this ceiling are aborted at the stream boundary with `HTTP 413 (Content Too Large)`.
- Rejection is recorded as an immutable audit event (`INGEST_REJECTED_TOO_LARGE`) with the declared filename and byte limit, and zero bytes are persisted to the database.

### 7.2 Zero-Disk-Write Streaming vs Multipart Spooling (DEC-012)
- **Multipart Framework Limitation:** Standard HTTP `POST /api/evidence/upload` utilizes Starlette / FastAPI `UploadFile`, which internally leverages Python's `tempfile.SpooledTemporaryFile`. For files exceeding 1 MiB, Starlette's underlying implementation spools buffer segments to local OS temporary directories.
- **Pure In-Memory Streaming:** To guarantee absolute compliance with Rule R4 (zero runtime forensic evidence disk writes) on large extractions, forensic clients and integrations should utilize `PUT /api/evidence/upload-stream`. This endpoint reads raw chunked streams directly into in-memory buffers without framework tempfile spooling.

### 7.3 ZIP Safety and Decompression Ceilings (R12)
- Ingested ZIP archives are parsed strictly in memory with hard enforcement of forensic safety ceilings:
  - **Member Count:** Maximum 10,000 members per archive.
  - **Uncompressed Size:** Maximum 1 GiB total uncompressed payload.
  - **Compression Ratio:** Maximum 100:1 expansion ratio per member.
  - **Path Traversal & Depth:** Rejection of path traversal (`../`) and directory nesting depth > 2.
- Violations result in exhibit status `ARCHIVE_REJECTED` and an `ARCHIVE_SAFETY_VIOLATION` audit log entry.

### 7.4 Deferred BYTEA Query Isolation (R19)
- Evidence exhibit binaries stored in PostgreSQL `BYTEA` (or SQLite `BLOB`) columns are configured with SQLAlchemy deferred loading (`deferred(Column(LargeBinary, ...))`).
- Bulk collection endpoints (`GET /api/evidence`) explicitly exclude `content_bytes` from the SQL column projection via `load_only()`, ensuring that querying case exhibits never causes memory exhaustion even with dozens of 256 MiB exhibits.
